## 1. Схема учебных данных

Синтетический маркетплейс (генератор — [datasets/generator.py](../../datasets/generator.py), схема — [datasets/schema.sql](../../datasets/schema.sql)):

```
users ─┬─< orders ─┬─< order_items >── products >── sellers
  ▲    │           │                      │
  └────┘ referred_by└─< payments          └──> categories ─┐ parent_id
       │                                          ▲        │
       ├─< reviews >── products                   └────────┘
       └─< events  (user_id может быть NULL — анонимы)
```

| Таблица | Что важно знать |
|---|---|
| `users` | `city` бывает NULL; `referred_by` — кто пригласил (дерево) |
| `categories` | дерево через `parent_id`; категория 25 пустая |
| `orders` | `status` — жизненный цикл; `promo_code` бывает NULL и «грязный» |
| `order_items` | `unit_price` — цена **на момент покупки**, не текущая цена товара |
| `payments` | у заказа 0..N платежей: неудачные попытки, успешные, возвраты. Бывают двойные списания |
| `events` | кликстрим: `view → add_to_cart → checkout → purchase`; `product_id` NULL у checkout/purchase |

Такие данные выбраны намеренно: NULL'ы, связи 1:N, деревья и «грязь» — это то, на чём ломаются запросы в продакшне.

## 2. Реляционная модель: что на самом деле делает SQL

### 2.1. Отношения, а не таблицы

Кодд (1970) определил **отношение** (relation) как *множество* кортежей с одинаковым набором атрибутов.
Ключевые свойства отношения в теории:

- порядка строк **нет**;
- дубликатов **нет** (это множество);
- порядка колонок нет (атрибуты адресуются по имени).

SQL от теории отступил: таблица в SQL — это **мультимножество** (bag), дубликаты разрешены. Отсюда
существование `DISTINCT`, `UNION` vs `UNION ALL`, и то, что `SELECT country FROM users` вернёт
300 строк, а не 8. Решение было прагматичным: устранение дубликатов требует сортировки или хеширования,
то есть стоит дорого.

> **Практическое следствие №1.** Без `ORDER BY` порядок строк **не определён**. Не «обычно по id», не
> «в порядке вставки», а *не определён*. Он меняется от плана выполнения: параллельный seq scan,
> hash join, synchronized scans (PostgreSQL может начать чтение таблицы с середины, «подсев» к
> идущему скану) — и твой «стабильный» порядок исчез. Код, который полагается на порядок без
> `ORDER BY`, — латентный баг.

### 2.2. Реляционная алгебра

Любой SQL-запрос — это выражение над отношениями из небольшого набора операторов:

| Оператор | Обозначение | SQL |
|---|---|---|
| Селекция (фильтр строк) | σ<sub>условие</sub>(R) | `WHERE` |
| Проекция (выбор колонок) | π<sub>колонки</sub>(R) | список `SELECT` |
| Декартово произведение | R × S | `CROSS JOIN`, `FROM a, b` |
| Соединение | R ⋈<sub>θ</sub> S = σ<sub>θ</sub>(R × S) | `JOIN ... ON` |
| Объединение / разность / пересечение | ∪, −, ∩ | `UNION`, `EXCEPT`, `INTERSECT` |
| Переименование | ρ | `AS` |
| Группировка/агрегация (расширение) | γ | `GROUP BY` |

Зачем это знать инженеру? **Оптимизатор разбирает запрос на такие операции и меняет их порядок**,
если результат от этого не меняется, а работы становится меньше. Этих правил перестановки три.
(Как читать значки: σ — фильтр, `WHERE`; π — выбор колонок, `SELECT a, b`; ⋈ — `JOIN`; R, S, T — таблицы.)

**1. Фильтр можно выполнить до соединения — *predicate pushdown*.**
Формула σ<sub>p</sub>(R ⋈ S) = σ<sub>p</sub>(R) ⋈ S означает: «соединить, потом отфильтровать» даёт
то же самое, что «отфильтровать, потом соединить», **если условие касается только одной таблицы**.

```sql
SELECT o.id, u.email
FROM orders o JOIN users u ON u.id = o.user_id
WHERE u.country = 'AM';
```

Буквально по тексту: соединить все 1500 заказов со всеми 300 пользователями, а из результата выбросить
всё, кроме Армении. Оптимизатор же сначала отфильтрует пользователей (останется 16) и соединять будет
только их. Ответ тот же, работы в разы меньше. В `EXPLAIN` видно, что фильтр «опустился» к чтению `users`:

```
Hash Join
  Hash Cond: (o.user_id = u.id)
  ->  Seq Scan on orders o
  ->  Hash
        ->  Seq Scan on users u
              Filter: (country = 'AM'::bpchar)     ← фильтр применён ДО соединения
```

**2. Порядок соединений можно менять — *join reordering* (только для INNER JOIN!).**
R ⋈ S = S ⋈ R и (R ⋈ S) ⋈ T = R ⋈ (S ⋈ T) — то же, что переместительный и сочетательный законы
для умножения: 2·3 = 3·2, (2·3)·4 = 2·(3·4). Для запроса `order_items JOIN orders JOIN users` порядок
таблиц в тексте ничего не значит. Оптимизатор сам выберет, что соединять первым — обычно то, что даёт
самый маленький промежуточный результат (например, сначала 16 пользователей из Армении, потом их
заказы, потом позиции этих заказов, а не все 2897 позиций сразу). Для 3 таблиц вариантов порядка
немного, для 10 — сотни тысяч. Поэтому выбор порядка соединений — самая сложная часть планировщика
(урок 05).

Для `LEFT JOIN` это правило **не работает**: `users LEFT JOIN orders` сохраняет всех пользователей,
а `orders LEFT JOIN users` — все заказы. Результаты разные, значит переставлять таблицы нельзя.

**3. Ненужные колонки можно отбросить раньше — *projection pushdown*.**
Выбор колонок и фильтр можно менять местами, если фильтру хватает оставшихся колонок. На практике
это значит, что оптимизатор тащит через соединения только те колонки, которые реально нужны дальше.
Поэтому `SELECT *` внутри подзапроса в PostgreSQL обычно ничего не стоит: лишние колонки выбрасываются.
В строковом PostgreSQL выигрыш небольшой (строка читается с диска целиком), а в колоночном ClickHouse
это главный источник скорости: колонки, не упомянутые в запросе, вообще не читаются с диска (урок 11).

Важно: **для внешних соединений эти эквивалентности частично не выполняются** — `LEFT JOIN` нельзя
произвольно переставлять, и фильтр нельзя бездумно протолкнуть через него. Поэтому переписывание
`INNER JOIN` в `LEFT JOIN` «на всякий случай» не только меняет семантику, но и связывает руки
оптимизатору. Вернёмся к этому в уроке 05.

### 2.3. Декларативность

Ты описываешь **что** нужно получить, а не **как**. Один и тот же запрос может выполниться сотней
способов (порядок соединений × алгоритмы соединений × способы доступа к таблицам), и выбирает их
планировщик на основе статистики. Отсюда главное правило этого урока:

> Сначала запрос должен быть **семантически корректен**, и только потом — быстр.
> Корректность ты проверяешь рассуждением о множествах строк, а не «вроде выдаёт похожие цифры».

## 3. Логический порядок выполнения SELECT

Текст запроса пишется в одном порядке, а *логически* вычисляется в другом:

```
 1. FROM / JOIN          — построить исходное множество строк (включая ON)
 2. WHERE                — отфильтровать строки
 3. GROUP BY             — сгруппировать
 4. HAVING               — отфильтровать группы
 5. оконные функции      — вычислить окна над результатом шага 4
 6. SELECT               — вычислить выражения, назначить алиасы
 7. DISTINCT             — убрать дубликаты
 8. UNION / INTERSECT / EXCEPT
 9. ORDER BY             — отсортировать
10. OFFSET / LIMIT       — отрезать
```

Это *логическая* модель — физически СУБД делает что угодно, лишь бы результат совпал. Но именно
логическая модель объясняет все «странности»:

- **Почему в `WHERE` нельзя использовать алиас из `SELECT`**: на шаге 2 алиасов ещё нет.
- **Почему в `ORDER BY` можно**: шаг 9 идёт после 6.
- **Почему в `WHERE` нельзя использовать оконную функцию** (`WHERE row_number() OVER (...) <= 3`):
  окна вычисляются на шаге 5. Нужен подзапрос/CTE.
- **Почему в `HAVING` можно агрегат, а в `WHERE` нельзя**: WHERE работает до группировки.
- **Почему оконная функция видит строки уже после `WHERE` и `GROUP BY`**: `sum(count(*)) OVER ()` —
  законная конструкция, это окно поверх агрегата (пригодится в task_20).
- **Почему `DISTINCT` + `ORDER BY` по колонке не из `SELECT` — ошибка**: после шага 7 такой колонки
  нет, и непонятно, по какой из «схлопнутых» строк сортировать.

> PostgreSQL разрешает в `GROUP BY` ссылаться на алиас или номер колонки (`GROUP BY 1`) — это
> расширение стандарта, удобное, но оно не меняет логической модели.

```sql
-- Проверь себя: почему этот запрос падает, и как его починить двумя способами?
SELECT user_id, count(*) AS cnt FROM orders WHERE cnt > 10 GROUP BY user_id;
```

## 4. NULL и трёхзначная логика

### 4.1. Что такое NULL

NULL — это **не значение**, а маркер отсутствия значения («неизвестно» или «неприменимо»). Любое
сравнение с неизвестным даёт неизвестный результат. Поэтому в SQL не две логические величины, а три:
`TRUE`, `FALSE`, `UNKNOWN` (в PostgreSQL `UNKNOWN` представлен как `NULL::boolean`).

| a | b | a AND b | a OR b | NOT a |
|---|---|---|---|---|
| TRUE | UNKNOWN | UNKNOWN | TRUE | FALSE |
| FALSE | UNKNOWN | **FALSE** | UNKNOWN | TRUE |
| UNKNOWN | UNKNOWN | UNKNOWN | UNKNOWN | UNKNOWN |

Способ запомнить: подставь вместо UNKNOWN «то ли TRUE, то ли FALSE». Если результат от этого не
зависит (`FALSE AND ?` = FALSE, `TRUE OR ?` = TRUE) — он определён, иначе UNKNOWN.

```sql
SELECT NULL = NULL, NULL <> NULL, NULL AND false, NULL OR true, NOT NULL::bool;
```

### 4.2. Кто и как интерпретирует UNKNOWN — асимметрия

| Контекст | Строка проходит, если условие... |
|---|---|
| `WHERE`, `HAVING`, `ON`, `CASE WHEN` | строго **TRUE** |
| `CHECK`-ограничение | **не FALSE** (TRUE или UNKNOWN) |

То есть `CHECK (price > 0)` пропустит `price = NULL`. Поэтому в схеме `price` объявлен `NOT NULL` —
CHECK сам по себе от NULL не защищает. Это частый дефект схем.

Следствие для `WHERE`: `WHERE city <> 'Москва'` **не вернёт** пользователей с `city IS NULL`.
Условие и его «отрицание» вместе не покрывают все строки:

```sql
SELECT count(*) FROM users;                                  -- 300
SELECT count(*) FROM users WHERE city =  'Москва';           -- a
SELECT count(*) FROM users WHERE city <> 'Москва';           -- b;  a + b < 300 !
SELECT count(*) FROM users WHERE city IS DISTINCT FROM 'Москва';  -- NULL-безопасное сравнение
```

### 4.3. Где NULL'ы считаются равными

Непоследовательно, но так устроен стандарт:

| Операция | NULL и NULL — это... |
|---|---|
| `=` в условиях | не равны (UNKNOWN) |
| `GROUP BY`, `DISTINCT`, `UNION`, `INTERSECT`, `EXCEPT` | **одна группа** («не различаются») |
| `UNIQUE`-ограничение | различны → можно много строк с NULL (с PG 15 есть `UNIQUE NULLS NOT DISTINCT`) |
| `ORDER BY` | по умолчанию NULL **больше** любых значений: в конце при `ASC`, в начале при `DESC` |

Последнее — ловушка: `ORDER BY rating DESC LIMIT 10` вернёт сначала строки с NULL. Используй `NULLS LAST`.

### 4.4. NULL в агрегатах

Агрегатные функции (кроме `count(*)`) **игнорируют NULL**:

| Выражение | Набор {5, NULL, 7} | Пустой набор | Набор {NULL, NULL} |
|---|---|---|---|
| `count(*)` | 3 | 0 | 2 |
| `count(x)` | 2 | 0 | 0 |
| `sum(x)` | 12 | **NULL** | **NULL** |
| `avg(x)` | 6 (не 4!) | NULL | NULL |
| `max(x)` | 7 | NULL | NULL |

Два практических вывода:

1. `sum()` по пустой группе — NULL, а не 0. В отчётах почти всегда нужен `coalesce(sum(x), 0)`.
2. `avg(x)` делит на число **не-NULL** значений. Если NULL означает «ноль» (например, «нет покупок»),
   `avg` соврёт — нужно `avg(coalesce(x, 0))`. Какой вариант правильный, определяет *бизнес-смысл*
   NULL, а не SQL.

`count(*) - count(col)` — идиоматичный способ посчитать NULL'ы в колонке (task_01).

### 4.5. Инструменты

- `x IS NULL`, `x IS NOT NULL` — единственный способ проверить на NULL.
- `a IS [NOT] DISTINCT FROM b` — сравнение, где NULL = NULL. Незаменимо в дедупликации и CDC-сравнениях
  «изменилась ли строка». (Важно: обычный индекс не используется для `IS DISTINCT FROM` — учтём в уроке 04.)
- `coalesce(a, b, ...)` — первое не-NULL.
- `nullif(a, b)` — NULL, если `a = b`. Классика: `x / nullif(y, 0)` вместо деления на ноль.

### 4.6. Главная ловушка: NOT IN

```sql
SELECT count(*) FROM products WHERE id NOT IN (SELECT product_id FROM events);
```

`x NOT IN (a, b, NULL)` раскрывается в `x <> a AND x <> b AND x <> NULL`. Последний член — UNKNOWN,
поэтому вся конъюнкция может быть только FALSE или UNKNOWN, но никогда TRUE. **Запрос вернёт 0 строк**,
если в подзапросе есть хоть один NULL. В `events.product_id` NULL'ы есть — это task_02.

Решение — `NOT EXISTS`: он проверяет существование строки, а не сравнивает значения, и NULL'ы его
не ломают. Правило для продакшн-кода: **`NOT IN` только со списком литералов, никогда с подзапросом.**

Кроме семантики, у `NOT IN` есть и проблема производительности: из-за NULL-семантики PostgreSQL не
может превратить его в anti-join (см. §6) и выполняет как `SubPlan` — хешированный, если подзапрос
влезает в `work_mem`, иначе — вложенный перебор O(N·M). Это исследовательская задача R1.

## 5. Соединения (JOIN)

### 5.1. Определение

Любое соединение логически — это декартово произведение с фильтром: `A JOIN B ON p` = все пары
(a, b), для которых `p` = TRUE. Внешние соединения добавляют «потерявшиеся» строки:

| Тип | Результат |
|---|---|
| `CROSS JOIN` | все пары, \|A\|·\|B\| строк |
| `[INNER] JOIN` | пары, где `ON` = TRUE |
| `LEFT JOIN` | INNER + строки A без пары (колонки B = NULL) |
| `RIGHT JOIN` | зеркально (на практике переписывают в LEFT) |
| `FULL JOIN` | INNER + непарные из A + непарные из B |

`USING (col)` — сахар для `ON a.col = b.col`, склеивающий колонку в одну; `NATURAL JOIN` — соединение
по всем одноимённым колонкам: **не используй в продакшне** — добавление колонки в таблицу тихо
меняет семантику запроса.

### 5.2. ON против WHERE во внешнем соединении

Для `INNER JOIN` условие можно писать хоть в `ON`, хоть в `WHERE` — результат тот же. Для `LEFT JOIN`
— нет, и это одна из самых частых ошибок в аналитике:

```sql
-- (1) Условие в ON: «присоединить только активные товары». Все категории сохраняются.
SELECT c.id, count(p.id)
FROM categories c LEFT JOIN products p ON p.category_id = c.id AND p.is_active
GROUP BY c.id;

-- (2) Условие в WHERE: сначала LEFT JOIN, потом фильтр. У категорий без товаров p.is_active = NULL,
--     WHERE отбрасывает их. LEFT JOIN молча превратился в INNER JOIN.
SELECT c.id, count(p.id)
FROM categories c LEFT JOIN products p ON p.category_id = c.id
WHERE p.is_active
GROUP BY c.id;
```

Правило: **фильтры по правой (nullable) таблице LEFT JOIN — в `ON`; по левой — в `WHERE`.**
Планировщик PostgreSQL, кстати, сам распознаёт случай (2) — условие `WHERE`, отвергающее NULL
(«strict»), — и превращает LEFT JOIN в INNER (*outer join reduction*). Это видно в `EXPLAIN`.

Заметь ещё: `count(p.id)`, а не `count(*)`. Для категории без товаров LEFT JOIN даёт одну строку с
NULL'ами — `count(*)` посчитает её как 1.

### 5.3. Кардинальность и размножение строк (fan-out)

Для каждой пары таблиц держи в голове отношение: 1:1, 1:N или N:M. Результат соединения по связи 1:N
содержит по строке на каждую пару — строка «одной» стороны **размножается**.

Самая дорогая ошибка аналитика: соединить *две независимые* 1:N-ветки и агрегировать.

```sql
-- Пользователь с 3 заказами, у каждого по 2 платежа. Что вернёт запрос?
SELECT u.id, count(o.id) AS orders_cnt, sum(p.amount) AS paid
FROM users u
LEFT JOIN orders o   ON o.user_id = u.id
LEFT JOIN payments p ON p.order_id = o.id
GROUP BY u.id;
```

`orders_cnt` окажется 6, а не 3: каждый заказ размножился на свои платежи. А если бы вместо
`payments` были `reviews` (тоже 1:N от пользователя, но **не** через заказ) — получилось бы
декартово произведение заказов на отзывы, и неверными стали бы *обе* метрики.

Это не редкий кейс — так ломаются дашборды выручки. Способы защиты:

1. **Агрегировать до соединения** — каждая ветка сворачивается до ключа «одной» стороны, потом
   соединяются уже 1:1:
   ```sql
   SELECT u.id, coalesce(o.cnt, 0), coalesce(p.paid, 0)
   FROM users u
   LEFT JOIN (SELECT user_id, count(*) cnt FROM orders GROUP BY 1) o ON o.user_id = u.id
   LEFT JOIN (SELECT o.user_id, sum(amount) paid FROM payments p JOIN orders o ON o.id = p.order_id
              GROUP BY 1) p ON p.user_id = u.id;
   ```
2. **Скалярные подзапросы / LATERAL** для каждой метрики.
3. `count(DISTINCT ...)` — работает для счётчиков, **но не для сумм** (`sum(DISTINCT amount)` сложит
   одинаковые суммы разных платежей один раз — ещё одна ошибка).

> **Привычка уровня senior.** После каждого JOIN спроси себя: «какой теперь *гранулярности* строка?»
> (одна строка = один заказ? одна позиция заказа? одна пара заказ×платёж?). Агрегаты осмысленны только
> если ты знаешь гранулярность. В DWH это называется *grain* факт-таблицы — вернёмся в уроке 12.

### 5.4. Самосоединение и неравенства

Соединение не обязано быть по равенству: `ON a.created_at < b.created_at` (θ-join), диапазоны
`ON e.created_at BETWEEN s.start AND s.end`. Такие соединения нельзя выполнить hash join'ом (он умеет
только равенство) — только nested loop или merge join. На больших таблицах это часто сигнал, что
задачу надо решать оконной функцией (например, «предыдущий заказ» — это `lag()`, а не самосоединение
с `max(created_at) where created_at < ...`).

## 6. Semi-join и anti-join

Часто нужно не соединить, а **проверить существование**: «пользователи, у которых есть заказ» (semi-join)
или «у которых нет» (anti-join). Ключевое свойство: каждая строка левой таблицы попадает в результат
**не более одного раза**, сколько бы пар ни нашлось. Обычный JOIN так не умеет — он размножает.

```sql
-- Semi-join: эквивалентные формы
SELECT * FROM users u WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);
SELECT * FROM users u WHERE u.id IN (SELECT user_id FROM orders);

-- Неправильная «эквивалентная» форма — размножает пользователей:
SELECT u.* FROM users u JOIN orders o ON o.user_id = u.id;
-- «чинить» её через DISTINCT — дорого и маскирует ошибку мышления.

-- Anti-join: правильные формы
SELECT * FROM users u WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);
SELECT u.* FROM users u LEFT JOIN orders o ON o.user_id = u.id WHERE o.id IS NULL;
```

`EXPLAIN` покажет у первых двух узел `Hash Semi Join` (или `Nested Loop Semi Join`), у anti-join'а —
`Hash Anti Join`. Это отдельные физические операторы: они останавливают поиск пары на первом
совпадении. `SELECT 1` в `EXISTS` — просто соглашение: список выборки подзапроса в `EXISTS` не
вычисляется.

В `LEFT JOIN ... IS NULL` проверяй колонку, которая **не может быть NULL** в правой таблице (PK
или колонка из условия соединения) — иначе строка с NULL в этой колонке будет принята за «пары нет».

## 7. Подзапросы и LATERAL

### 7.1. Виды подзапросов

| Вид | Возвращает | Где | Пример |
|---|---|---|---|
| Скалярный | 1 строка × 1 колонка (или 0 строк → NULL) | где угодно вместо значения | `(SELECT avg(price) FROM products)` |
| Табличный (derived table) | отношение | `FROM` | `FROM (SELECT ...) t` |
| Для предикатов | множество | `IN`, `EXISTS`, `ANY/ALL` | `WHERE id IN (SELECT ...)` |

Скалярный подзапрос, вернувший 2+ строки, — **ошибка времени выполнения**, а не компиляции. Такой
запрос может годами работать и упасть, когда в данных появится дубликат. Если уникальность не
гарантирована ограничением — не полагайся на неё.

### 7.2. Коррелированные подзапросы

Подзапрос, ссылающийся на колонки внешнего запроса, логически выполняется **для каждой строки**
внешнего. Физически PostgreSQL умеет «раскоррелировать» (*pull up*) подзапросы в `IN`/`EXISTS` —
превратить их в semi/anti-join. Но коррелированные **скалярные** подзапросы в `SELECT` и `WHERE`
он в соединения **не превращает** (в отличие от, например, SQL Server или Oracle) — это
`SubPlan`, выполняемый на каждую строку. На 100 строк — неважно, на 10 млн — катастрофа
(исследование R3).

### 7.3. LATERAL

Обычный подзапрос в `FROM` не видит соседние таблицы — он вычисляется независимо. `LATERAL`
разрешает ссылаться на таблицы левее — это «цикл for в SQL»: для каждой строки слева выполнить
подзапрос справа.

```sql
-- Два последних заказа каждого пользователя из Армении
SELECT u.id, o.id, o.created_at
FROM users u
CROSS JOIN LATERAL (
    SELECT id, created_at FROM orders
    WHERE user_id = u.id
    ORDER BY created_at DESC LIMIT 2
) o
WHERE u.country = 'AM';
```

`LEFT JOIN LATERAL (...) ON true` — чтобы сохранить строки слева без результата.

Когда LATERAL выигрывает: **top-N в группе при наличии индекса** `(user_id, created_at DESC)` —
для каждого пользователя делается короткий index scan и остановка после N строк. Оконная функция
же обязана прочитать и пронумеровать *все* строки. На 1000 пользователей с миллионами заказов —
разница в порядки. А без индекса LATERAL — это N полных сканирований, и окно выигрывает.
Правильный выбор зависит от данных и индексов — это типичный вопрос на собеседовании.

## 8. Агрегация: FILTER, GROUPING SETS

### 8.1. Условная агрегация

```sql
SELECT
    count(*)                                        AS all_orders,
    count(*) FILTER (WHERE status = 'cancelled')    AS cancelled,
    sum(amount) FILTER (WHERE status = 'succeeded') AS paid
FROM ...
```

`FILTER` — стандартный SQL (в PostgreSQL с 9.4), эквивалентен `count(CASE WHEN ... THEN 1 END)`, но
читаемее. Позволяет посчитать много срезов **за один проход** по данным вместо `UNION` нескольких
запросов — это основной приём построения отчётов и воронок (task_24).

Полезные агрегаты: `bool_or`/`bool_and` (есть ли хоть одна / все ли строки удовлетворяют),
`string_agg(x, ', ' ORDER BY x)`, `array_agg(x ORDER BY y)`, `percentile_cont(0.5) WITHIN GROUP
(ORDER BY x)` — медиана, `mode() WITHIN GROUP (ORDER BY x)`.

### 8.2. HAVING

Фильтр по группам после агрегации. Условия, не зависящие от агрегатов, пиши в `WHERE` — они
выполнятся до группировки и сократят объём работы (хотя планировщик часто переносит их сам).

### 8.3. GROUPING SETS, ROLLUP, CUBE

Несколько группировок за один проход:

```sql
GROUP BY GROUPING SETS ((country, status), (country), ())
-- то же самое:
GROUP BY ROLLUP (country, status)      -- иерархия: (c,s), (c), ()
GROUP BY CUBE (country, status)        -- все комбинации: (c,s), (c), (s), ()
```

В строках подытогов «свёрнутые» колонки заполняются NULL. Чтобы отличить такой NULL от NULL в
данных, есть `GROUPING(col)` — возвращает 1, если колонка свёрнута в этой строке:

```sql
SELECT CASE WHEN GROUPING(country) = 1 THEN 'ИТОГО' ELSE country END, ...
```

Это то, что делает под капотом любой BI-инструмент со «строкой итогов». В OLAP-части курса увидишь,
как ClickHouse делает это `WITH ROLLUP/CUBE/TOTALS`.

## 9. Оконные функции

Самая важная тема урока. На собеседованиях в бигтех задачи на окна — обязательная часть SQL-секции.

### 9.1. Модель

Агрегат с `GROUP BY` **схлопывает** группу в одну строку. Оконная функция вычисляет значение по
группе строк («окну»), но **сохраняет** каждую строку.

```sql
SELECT id, user_id, created_at,
       count(*) OVER (PARTITION BY user_id)                       AS user_orders,
       row_number() OVER (PARTITION BY user_id ORDER BY created_at) AS nth_order
FROM orders;
```

Окно задаётся тремя компонентами:

```
func(...) OVER (
    PARTITION BY ...     -- на какие независимые группы делить (как GROUP BY, но без схлопывания)
    ORDER BY ...         -- порядок строк внутри раздела
    frame                -- какие строки относительно текущей входят в окно
)
```

### 9.2. Семейства функций

| Семейство | Функции | Используют фрейм? |
|---|---|---|
| Ранжирующие | `row_number`, `rank`, `dense_rank`, `percent_rank`, `cume_dist`, `ntile(n)` | нет, только ORDER BY |
| Смещения | `lag(x, n, default)`, `lead(...)` | нет |
| Значения из фрейма | `first_value`, `last_value`, `nth_value` | **да** |
| Любой агрегат | `sum`, `avg`, `count`, `min`, `max`, `bool_or`, ... | **да** |

Разница ранжирующих — на равных значениях (ценах 100, 100, 90):

| price | row_number | rank | dense_rank |
|---|---|---|---|
| 100 | 1 | 1 | 1 |
| 100 | 2 | 1 | 1 |
| 90 | 3 | **3** | **2** |

`row_number` при равенстве нумерует **произвольно** (недетерминированно!) — если результат важен,
добавляй в `ORDER BY` окна тай-брейк по уникальной колонке.

### 9.3. Фреймы — то, что знают немногие

Фрейм определяет подмножество строк раздела для агрегатов и `first/last/nth_value`:

```
{ ROWS | RANGE | GROUPS } BETWEEN <начало> AND <конец> [EXCLUDE ...]
  <начало>/<конец>: UNBOUNDED PRECEDING | n PRECEDING | CURRENT ROW | n FOLLOWING | UNBOUNDED FOLLOWING
```

- `ROWS` — смещение в физических строках: «6 строк назад».
- `RANGE` — смещение по **значению** ключа сортировки: `RANGE BETWEEN interval '6 days' PRECEDING AND
  CURRENT ROW` — все строки, чья дата в пределах 6 дней от текущей (требует ровно одну колонку в ORDER BY).
- `GROUPS` — смещение в группах *равных* значений (peers).

**Фрейм по умолчанию** — источник классических багов:

- без `ORDER BY` — весь раздел;
- с `ORDER BY` — `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`, причём `CURRENT ROW` в режиме
  `RANGE` означает «текущая строка **и все её peers**» (строки с тем же значением ORDER BY).

Два следствия:

```sql
-- 1. Нарастающий итог «перескакивает» на равных значениях:
SELECT day, amount, sum(amount) OVER (ORDER BY day) FROM t;
-- если на один день 3 строки, все три получат одинаковую сумму, включающую все три.
-- Для построчного нарастающего итога: ORDER BY day, id ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW

-- 2. last_value() «не работает»:
SELECT last_value(price) OVER (PARTITION BY category_id ORDER BY price) FROM products;
-- вернёт текущую цену (конец фрейма = текущая строка), а не максимальную.
-- Нужен явный фрейм: ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
```

`EXCLUDE CURRENT ROW | GROUP | TIES` — исключить текущую строку/peers из фрейма («средняя цена
по категории *без* этого товара»).

### 9.4. Как это выполняется

Узел `WindowAgg` получает строки, **отсортированные** по `PARTITION BY` + `ORDER BY`. Если индекс не
даёт готового порядка — будет `Sort`, то есть O(N log N) и, возможно, сортировка на диске при
нехватке `work_mem`. Несколько окон с разными `PARTITION BY/ORDER BY` в одном запросе → несколько
сортировок. Одинаковые окна выноси в `WINDOW w AS (...)` — читаемость, и планировщик гарантированно
посчитает их за одну сортировку.

Фильтровать по оконной функции можно только уровнем выше (`WHERE` вычисляется раньше окон). С
PostgreSQL 15 для `row_number() ... WHERE rn <= N` планировщик умеет *run condition* —
останавливать подсчёт окна, когда условие перестаёт выполняться.

### 9.5. Паттерны, которые надо уметь с листа

**Нарастающий итог и доля от целого:**
```sql
sum(x) OVER (ORDER BY day ROWS UNBOUNDED PRECEDING)
x / sum(x) OVER ()                      -- доля в общем итоге
sum(count(*)) OVER ()                   -- окно поверх агрегата GROUP BY
```

**Скользящее среднее:**
```sql
avg(x) OVER (ORDER BY day ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)
```
Ловушка: `ROWS` считает строки, а не дни. Если дней без данных нет в выборке, «7 строк» могут
покрыть месяц. Сначала заполни дыры: `generate_series` + `LEFT JOIN` (task_14, task_15), или
используй `RANGE ... interval`.

**Сравнение с предыдущим:**
```sql
x - lag(x) OVER (PARTITION BY user_id ORDER BY created_at)   -- дельта / интервал между событиями
```

**Top-N в группе и дедупликация:**
```sql
SELECT * FROM (
  SELECT *, row_number() OVER (PARTITION BY user_id ORDER BY created_at DESC, id DESC) rn FROM orders
) t WHERE rn = 1;
```

**Gaps and islands** — найти непрерывные серии. Трюк: если значения идут подряд, то
`значение − row_number()` постоянно внутри серии и меняется между сериями:

```
месяц (как число)  row_number  разность  → остров
      5                1           4        A
      6                2           4        A
      7                3           4        A
      9                4           5        B
     10                5           5        B
```
Группируешь по разности — получаешь острова (task_18).

**Сессионизация** — второй вариант островов: «новый остров начинается, если выполнено условие».
Флаг начала (`CASE WHEN gap > 30 min THEN 1 ELSE 0 END`), затем нарастающая сумма флагов даёт номер
сессии (task_19). Этот приём — основа всей продуктовой аналитики, в ClickHouse он будет выглядеть
иначе, но идея та же.

## 10. CTE и рекурсия

### 10.1. Обычные CTE

`WITH x AS (...)` — именованный подзапрос. Главная ценность — читаемость: запрос читается сверху
вниз как конвейер шагов.

Производительность. До PostgreSQL 12 CTE **всегда** материализовались — вычислялись целиком в
временный результат, и внешние условия внутрь не проталкивались («optimization fence»). Со 12-й
версии CTE, на который ссылаются **один раз** и который не имеет побочных эффектов, **инлайнится**
как обычный подзапрос. Управлять можно явно:

```sql
WITH x AS MATERIALIZED (...)       -- вычислить один раз (полезно, если дорогой и используется много раз)
WITH x AS NOT MATERIALIZED (...)   -- инлайнить, даже если ссылок несколько
```

В других СУБД поведение разное, и в старых статьях совет «CTE тормозят» — про PG ≤ 11.

### 10.2. Рекурсивные CTE

```sql
WITH RECURSIVE tree AS (
    SELECT id, name, parent_id, 1 AS depth          -- (1) нерекурсивная часть: «якорь»
    FROM categories WHERE parent_id IS NULL
  UNION ALL
    SELECT c.id, c.name, c.parent_id, t.depth + 1   -- (2) рекурсивная часть
    FROM categories c JOIN tree t ON c.parent_id = t.id
)
SELECT * FROM tree;
```

Алгоритм выполнения (важно понимать — это не рекурсия, а **итерация**):

1. Выполнить якорь → результат положить в выход и в *рабочую таблицу*.
2. Выполнить рекурсивную часть, где `tree` — это **только рабочая таблица** (строки предыдущей
   итерации, а не весь накопленный результат).
3. Новые строки → в выход и в новую рабочую таблицу.
4. Повторять, пока рабочая таблица не станет пустой.

Отсюда: для обхода дерева глубины d делается d итераций, каждая — соединение «фронта» с таблицей.

**Циклы.** Если в графе есть цикл, `UNION ALL` будет крутиться бесконечно. Защиты:

- `UNION` вместо `UNION ALL` — отбрасывает строки, уже бывшие в результате. Работает, только если
  строки при повторном посещении **идентичны** — колонка `depth` это ломает.
- Хранить путь: `path || id` и условие `WHERE NOT c.id = ANY(t.path)`.
- PostgreSQL 14+: декларативно `CYCLE id SET is_cycle USING path`.
- Ограничитель глубины `WHERE depth < 100` — страховка от плохих данных в любом случае.

`SEARCH DEPTH FIRST BY id SET ord` / `SEARCH BREADTH FIRST` (PG 14+) — управляет порядком обхода
для сортировки результата «как дерево».

Применения: деревья категорий, оргструктуры, реферальные цепочки, графы зависимостей, BOM
(спецификации изделий), генерация последовательностей. Альтернативы для деревьев, которые часто
читаются и редко меняются: `ltree` (materialized path), nested sets, closure table — обсудим в уроке 02.

## 11. Операции над множествами и DISTINCT ON

### 11.1. UNION / INTERSECT / EXCEPT

- Без `ALL` — семантика **множеств**: дубликаты удаляются (сортировка или хеширование → дорого).
- С `ALL` — мультимножества: `UNION ALL` просто склеивает потоки, почти бесплатно.

Правило: **всегда `UNION ALL`, если дубликаты невозможны или нужны**. `UNION` «по привычке» —
лишняя сортировка на миллионах строк.

Приоритет: `INTERSECT` связывает сильнее, чем `UNION` и `EXCEPT` (как умножение и сложение).
`A EXCEPT B INTERSECT C` = `A EXCEPT (B INTERSECT C)`. Ставь скобки явно.

Колонки сопоставляются **по позиции**, не по имени. `SELECT a, b ... UNION SELECT b, a ...` молча
перепутает данные, если типы совместимы.

### 11.2. DISTINCT ON (расширение PostgreSQL)

```sql
SELECT DISTINCT ON (user_id) user_id, id, created_at
FROM orders
ORDER BY user_id, created_at DESC, id DESC;
```

Оставляет **первую** строку каждой группы `user_id` в порядке `ORDER BY`. Выражения `DISTINCT ON`
должны совпадать с началом `ORDER BY`. Компактнее, чем `row_number()`, и часто быстрее (одна
сортировка, без вычисления номеров). Но это не стандарт — в ClickHouse аналог `LIMIT 1 BY user_id`,
в других СУБД — только окна.

## 12. Типы, которые чаще всего ломают прод

### 12.1. Деньги: numeric, не float

`float8` — двоичная плавающая точка (IEEE 754). Десятичные дроби вроде 0.1 в ней **не
представимы точно**:

```sql
SELECT 0.1::float8 + 0.2::float8 = 0.3::float8;   -- false
SELECT 0.1::numeric + 0.2::numeric = 0.3;          -- true
```

`numeric(p, s)` — десятичное число произвольной точности, считает как на бумаге. Цена — скорость
(программная арифметика, а не аппаратная) и размер. Для денег — только `numeric` или целые
«копейки» в `bigint`. Для метрик, где погрешность допустима (средние, доли), `float` нормален.

Деление целых — целочисленное: `SELECT 1 / 3` → 0. Поэтому в процентах пиши `100.0 * a / b`.

### 12.2. Время: timestamptz и полуинтервалы

- `timestamptz` хранит **момент времени** в UTC (8 байт, микросекунды от 2000-01-01). Часовой пояс
  *не хранится* — при выводе значение переводится в `TimeZone` сессии.
- `timestamp` (without time zone) — «показания настенных часов» без привязки к поясу. Для событий
  почти всегда нужен `timestamptz`.
- Следствие: `created_at::date` и `date_trunc('day', created_at)` **зависят от часового пояса сессии**.
  Одна и та же выручка «за день» разная в Москве и в UTC. В отчётах пояс фиксируют явно:
  `(created_at AT TIME ZONE 'Europe/Moscow')::date`. Тесты курса работают в UTC.

**Фильтр по периоду — всегда полуинтервал:**

```sql
WHERE created_at >= '2024-03-01' AND created_at < '2024-04-01'     -- правильно
WHERE created_at BETWEEN '2024-03-01' AND '2024-03-31'             -- теряет 31 марта после 00:00
WHERE date_trunc('month', created_at) = '2024-03-01'               -- верно, но убивает индекс
WHERE extract(month FROM created_at) = 3                           -- то же + забыл про год
```

Два последних варианта называются *non-sargable*: функция над колонкой не даёт использовать
индекс по `created_at`. В уроке 04 это увидишь в планах.

### 12.3. generate_series — заполнение дыр

Отчёт «по дням» из `GROUP BY day` не содержит дней без событий — на графике они просто исчезнут,
а скользящие средние посчитаются неверно. Решение — «календарь» + `LEFT JOIN`:

```sql
SELECT d::date AS day, coalesce(s.cnt, 0)
FROM generate_series('2024-03-01'::date, '2024-03-31'::date, interval '1 day') d
LEFT JOIN (SELECT created_at::date AS day, count(*) cnt FROM orders GROUP BY 1) s ON s.day = d::date;
```
